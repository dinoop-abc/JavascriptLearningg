# Source Code vs Bytecode vs Binary Code

## Example File: `01_hellowword.js`

```javascript
console.log("hellow world");
```

---

## Comparison Table

| Aspect | Source Code | Bytecode | Binary Code |
|--------|-------------|----------|-------------|
| **Definition** | Human-readable instructions written in a programming language | Intermediate representation between source code and machine code | Machine-readable instructions executed directly by the CPU (0s and 1s) |
| **Readability** | Readable by humans | Partially readable (looks like cryptic text/numbers) | Not readable by humans without disassembly |
| **Example** | `console.log("hellow world");` | `0x26 0x03 0x43 0x00 0x01` (V8 Ignition bytecode) | `10110000 01100001 ...` (x86-64 machine code) |
| **File Extension** | `.js`, `.py`, `.java`, `.c` | `.class` (Java), `.pyc` (Python), internal (V8) | `.exe`, `.dll`, `.o`, `.out` (no extension on Linux) |
| **Who/What Processes It** | Written by **programmers**, read by **compilers/interpreters** | Generated by **compilers**, executed by **virtual machines (VMs)** | Generated by **assemblers/linkers**, executed directly by **CPU** |
| **Speed of Execution** | Slowest (must be interpreted/compiled first) | Faster than source, slower than binary (needs VM) | Fastest (runs natively on hardware) |
| **Portability** | Highly portable (runs anywhere with the right interpreter/compiler) | Portable across platforms with the same VM | Not portable (tied to specific CPU architecture, e.g., x86 vs ARM) |
| **Example in JavaScript Pipeline** | **You write this:** `console.log("hellow world");` | **V8 engine converts to:** Ignition bytecode (a compact, VM-readable format) | **TurboFan compiles hot code to:** Native machine instructions (x86/ARM) |
| **Can You Modify It?** | Yes — easily editable in any text editor | Difficult — requires bytecode editing tools | Extremely difficult — requires hex editor or disassembler |
| **Security** | Open — anyone can read it | Obfuscated but still analyzable | Harder to reverse-engineer (but possible) |

## How It Works for Your JavaScript File

```
 01_helloword.js (Source Code)
         │
         ▼
   ┌─────────────────────────┐
   │   V8 Parser             │  Parses source into AST (Abstract Syntax Tree)
   └─────────┬───────────────┘
             ▼
   ┌─────────────────────────┐
   │  Ignition (Interpreter) │  Generates Bytecode
   │     (Bytecode)          │
   └─────────┬───────────────┘
             ▼
   ┌─────────────────────────┐
   │  TurboFan (Compiler)    │  Compiles hot (frequently used) bytecode
   │    (Binary/Machine Code)│  into native CPU instructions
   └─────────┬───────────────┘
             ▼
        ┌──────────┐
        │   CPU    │  Executes binary instructions directly
        └──────────┘
           Result
     "hellow world" printed
          on screen
```

---

## Key Takeaway

1. **Source Code** (`console.log("hellow world");`) — What **you** write. Human-friendly.
2. **Bytecode** (internal V8 representation) — What the **JavaScript engine** generates. VM-friendly.
3. **Binary Code** (x86 machine instructions) — What the **CPU** executes. Machine-friendly.

JavaScript is an **interpreted language** (with JIT compilation), meaning it goes through all three stages at runtime, not ahead-of-time like C or C++.
